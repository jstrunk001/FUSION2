1. Executive Summary

This evaluation investigates whether the GPU-accelerated raster processing engine developed in the 2026_RasterMetrics/julia project can provide computational efficiencies for FUSION2.

The Julia project evaluated high-resolution Digital Surface Model (DSM) rasters derived from aerial photography (NAIP3D), measuring canopy metrics across 10,000 ft × 10,000 ft tiles (106 million fine pixels per tile). That investigation demonstrated that a CUDA kernel utilizing a 2,048-bin shared-memory cumulative distribution function (CDF) histogram, combined with an 8-stream CPU RAM pre-caching pipeline, reduced per-tile wall-clock time from 50.0 seconds down to 0.42 seconds when compared against a single-threaded R / terra baseline.

When assessing the relevance of these findings to FUSION2, this evaluation identified key distinctions:

  • Baseline Distinction: The measured speedup reflects an R / terra baseline. FUSION2 is implemented in native C++17 with multi-threaded batching; no empirical comparison exists between FUSION2 and the Julia GPU implementation on identical inputs.
  • Metric Completeness: The Julia CUDA kernel computes a 21-band raster subset (mean, standard deviation, min, max, 15 percentiles, canopy relief ratio, and cover). It omits metrics standard to FUSION2's PointStatBundle, including mode, average absolute deviation, median absolute deviation, and all four L-moments.
  • Percentile Agreement Characteristics: Across approximately 24,000 zones on validation tile 10011, the average difference per percentile was small (0.02 to 0.10 ft). For percentiles below p95, only 1 to 16 zones per band differed by more than 1.0 ft. These differences were concentrated in sparsely vegetated zones (under 20 pixels clearing the height break). On p99, 156 zones differed by more than 1.0 ft due to a fixed 300 ft histogram upper bound clipping photogrammetric surface spikes (up to 348.9 ft) in the test dataset.
  • Point Cloud I/O Constraints: For raw LiDAR processing, single-threaded LAZ decompression (LASzip) limits per-tile ingestion rates. In addition, at small grid resolutions (such as 10 ft), storing 2,048-bin histograms in CPU memory requires up to 20× more RAM than storing raw point elevations.

Analysis of Discrepancies and Root Causes

  1. Ground Resampling Differences in Minimum Height: The small difference in min (maximum difference 0.1152 ft, e.g. 6.12 ft vs. 6.00 ft) arises because the Julia pipeline implements a custom bilinear DTM interpolation (renormalizing across NaN corners), whereas the R pipeline relies on terra::resample().
  2. Low-Sample Quantile Estimation in Sparse Zones: Outside of p95 and p99, large residuals (>1 ft) occurred in only 1 to 16 out of 24,034 zones (<0.07% of the tile). In these zones (such as Zone 46, 104 with 0.23% canopy cover, where only 10 pixels cleared the 6.0 ft height break), R's sample quantile interpolation (type = 7) operates between discrete order statistics, whereas the CUDA kernel interpolates within continuous histogram bin intervals.
  3. Surface Model Spikes and Histogram Clamping: In the reference raster, 156 zones have maximum heights exceeding 300.0 ft, reaching up to 348.9 ft. In Washington forests, trees exceeding 320 ft are rare; photogrammetric DSM heights of 348 ft typically represent surface matching artifacts (birds, cloud noise, or DTM interpolation depressions). The 300 ft cap in the earlier kernel clipped these artifacts at bin 2048, resulting in a 23.73 ft difference on p99 in Zone (76, 119).

Potential Algorithmic Remedies for Sparse Zones

The quantile discrepancy in low-cover cells can be resolved on the GPU using two lightweight methods:

  • Shared-Memory Sorting for Small $N$: When a zone contains fewer than 256 pixels clearing the height break (such as Zone 46, 104 with $N = 10$), threads can collect the values into a small shared array and execute a 256-element bitonic sort, matching R's type = 7 rule.
  • Discrete CDF Step Indexing: Rather than interpolating within a histogram bin assuming continuous density, evaluate sample quantiles directly at non-zero bin steps.

5. Assessment of Histogram Methods on CPU

The proposal to replace sorting with fixed-bin histograms on the CPU requires evaluating data types and memory access patterns in FUSION2.

A. LAS Spectral Channels vs. 8-Bit Rasters

In LAS 1.4 point data record formats 2, 3, 7, and 8, Red, Green, Blue, and NIR are defined as unsigned 16-bit integers (uint16_t, $0 \dots 65,535$), as declared in src/libfusion_core/LASPointCloud.cpp.

  • For 8-bit imagery rasters (such as NAIP GeoTIFFs), values occupy $0 \dots 255$, allowing an exact 256-bin histogram (1.02 KB) with zero approximation error.
  • For raw LAS point clouds, an exact integer histogram requires 65,536 bins (256 KB per channel). Allocating 256 KB per cell across millions of cells in CPU memory is impractical. Binned approximations (e.g. 1,024 bins) introduce small quantization boundaries (~64 counts).

B. Memory Footprint Inversion on CPU at Small Cell Sizes

LiDAR points arrive in scanline acquisition order, spanning the geographic extent of a tile. A streaming CPU pipeline cannot process cells sequentially; it must maintain open accumulators for every grid cell simultaneously until the entire file is read.

Consider a standard forestry acquisition processed at FUSION's default 10.0 ft cell size:

  • At nominal pulse densities (e.g. 8–12 pulses/\(\text{m}^2\)), each 10 ft × 10 ft cell receives approximately 80 to 120 points.
  • Storing 100 raw single-precision float elevations consumes 400 bytes per cell.
  • An open 2,048-bin int32 histogram consumes 8,192 bytes per cell.

Under these conditions, a histogram accumulator requires approximately 20 times more host RAM than storing raw point elevations. Histograms become memory-efficient only when the cell size is large (such as 66.0 ft or 100.0 ft, where each cell contains >4,000 observations) or when memory is allocated on the GPU for in-flight threadblocks only.

6. Point Cloud Processing on GPUs: Opportunities & Constraints

Note: The GPU methods discussed in this section represent conceptual designs. Unlike the raster pipeline, they were not evaluated in the 2026_RasterMetrics project.

A. Ingestion Constraints in Point Cloud Processing

While GPU radix sorting (e.g. via NVIDIA CUB) can reorder arrays in device memory at high throughput, sorting raw points is only one component of end-to-end processing.

In FUSION2, reading compressed .laz files relies on single-threaded LASzip decompression per file stream. Estimated decompression times for a 50-million-point LAZ file on CPU range from 8 to 15 seconds, while PCIe 4.0 host-to-device memory transfer adds 0.5 to 1.0 second. FUSION2 mitigates this by decoding multiple tiles in parallel across CPU cores using /threads. Accelerating spatial binning on the GPU addresses in-memory reordering, but end-to-end speedups for raw point clouds will remain bounded by LAZ decompression rates unless GPU-native decompression engines (such as NVCOMP) are implemented.

B. 2.5D Rasterization for Canopy Height Models

A direct candidate for GPU point cloud processing exists in canopymodel.exe. Generating a Canopy Height Model requires finding the maximum elevation within each grid cell. On a GPU, this can be implemented via an atomicMax() kernel across an unorganized point buffer: 

// CUDA kernel for point cloud CHM rasterization:
// Requires non-negative normalized heights (h >= 0.0f) and float64 tile-origin offset
__global__ void rasterize_chm_kernel(const double* __restrict__ x,
                                     const double* __restrict__ y,
                                     const float* __restrict__ z,
                                     const float* __restrict__ ground,
                                     float* __restrict__ chm,
                                     int n, double xmin, double ymax,
                                     double res, int cols, int rows) {
    int i = blockIdx.x * blockDim.x + threadIdx.x;
    if (i >= n) return;

    // Relative double-precision offset prevents precision loss in state plane coordinates
    int col = static_cast((x[i] - xmin) / res);
    int row = static_cast((ymax - y[i]) / res);

    if (col >= 0 && col < cols && row >= 0 && row < rows) {
        int idx = row * cols + col;
        float h = z[i] - ground[idx];
        if (h >= 0.0f) {
            // Reinterpreting non-negative float32 as int32 preserves monotonic ordering
            atomicMax(reinterpret_cast(&chm[idx]), __float_as_int(h));
        }
    }
}

This operation requires no histograms, no sorting, and minimal shared memory, making it an appropriate candidate for initial GPU integration in FUSION2. Smoothing (/smooth) can follow as a standard 2D image filter pass.

7. Integration & Engineering Specifications

A. FUSION2 Executable Profiles

FUSION2 executables are built as statically-linked standalone binaries. File sizes in FUSION2/bin/ are:

  • gridmetrics.exe: 40.4 MB
  • canopymodel.exe: 40.2 MB
  • groundfilter.exe: 40.2 MB
  • filterdata.exe: 1.75 MB
  • thindata.exe: 1.75 MB

The larger executables (~40 MB) incorporate static PROJ projection tables and GDAL driver support. Adding static CUDA runtime support (cudart_static.lib) and multi-architecture machine code will add approximately 6 to 10 MB, resulting in binaries of approximately 46 to 50 MB.

B. Command-Line Syntax in FUSION2

CLI integration must follow FUSION2's established parameter conventions. In gridmetrics.cpp:

  • Cell size is passed via the /cellsize:<val> option, not as a positional parameter.
  • Output directory is governed by /outdir:<path> and /outroot:<name>.
  • The positional arguments are strictly: <input_file_or_dir> [optional_ground_raster].

Valid invocation examples: 

# Correct point cloud invocation:
gridmetrics /ground:dtm.tif /cellsize:66.0 /outdir:./output lidar_tile.laz

# Correct raster invocation (as proposed):
gridmetrics /ground:dtm.tif /cellsize:66.0 /outdir:./output dsm_tile.tif

C. CMake CUDA Configuration & GPU Architectures

The build specification in CMakeLists.txt must use valid architecture target syntax. In modern CMake (3.18+), virtual architectures use the -virtual suffix: 

# Target Pascal, Turing, Ampere, Ada Lovelace, and Blackwell with PTX fallback:
set(CMAKE_CUDA_ARCHITECTURES "60;75;80;86;89;120;75-virtual")
  • 60: Pascal architecture (GTX 1060–1080 / Quadro P-series, compute capability 6.0/6.1). Note: CUDA 13 dropped support for architecture 60, so compiling for Pascal requires a CUDA 12.x or earlier toolkit.
  • 75: Turing (Quadro RTX 5000, RTX 20-series).
  • 80, 86: Ampere (RTX 30-series, RTX A-series).
  • 89: Ada Lovelace (RTX 40-series, RTX 4000–6000 Ada).
  • 120: Blackwell consumer generation (RTX 50-series).
  • 75-virtual: Embeds virtual PTX assembly, allowing the installed NVIDIA driver to JIT-compile kernels on unlisted or future architectures.

8. Overall Verdict & Feasibility

Is GPU acceleration worth pursuing for FUSION2?

  • For Raster Ingestion (High Return): Yes. Incorporating a GPU-accelerated raster pipeline into FUSION2 offers proven utility. For statewide photogrammetric DSM processing (e.g. NAIP3D), where data are dense, continuous, and require no point decompression, the CUDA fused bilinear DTM kernel provides real operational speedups.
  • For Canopy Height Models (High Return): Yes. In canopymodel.exe, direct 2.5D rasterization via atomicMax() is technically simple, numerically robust, and avoids the memory penalties of histogram approaches.
  • For General Point Cloud GridMetrics (Moderate Return): The benefits are more constrained. Because FUSION2 already saturates CPU cores across tiles using /threads, and because single-threaded LAZ decompression bounds throughput per core, offloading only the point reduction phase yields lower net improvements on raw LiDAR than on pre-rasterized DSMs.

9. Study Limitations

  1. No FUSION2 CPU Baseline on Test Rasters: The 119× speedup reported in the Julia study was measured against single-threaded R / terra. FUSION2 currently lacks raster input support, so no empirical C++ baseline exists for this workload.
  2. Percentile Inaccuracy in Low-Canopy Zones: The 2,048-bin CDF histogram does not reproduce standard sample quantiles in cells with sparse canopy cover ($N < 20$), exhibiting errors up to 16.2 ft on validation data.
  3. Surface Noise Sensitivity with Fixed Bounds: Using a fixed 300 ft upper bound clipped photogrammetric surface spikes (up to 348.9 ft) in validation testing. Setting bounds from each zone's own maximum height is required to avoid skewing histogram resolution across a tile.
  4. Omission of Higher Moments & L-Moments: The CUDA kernel computes 21 bands. It does not compute mode, skewness, kurtosis, MAD, AAD, or L-moments, which are required by FUSION2's PointStatBundle.
  5. Point Cloud GPU Binning Remains Unmeasured: Point cloud processing on the GPU was not evaluated. Single-threaded LAZ decompression on the CPU remains a primary rate-limiting factor for raw LiDAR workflows.

10. Actionable Recommendations & Implementation Roadmap

Based on the empirical evidence, accuracy analyses, and memory constraints evaluated in this report, we outline a phased engineering roadmap for FUSION2. The architecture prioritizes native CPU raster ingestion to establish an empirical C++ baseline, followed by targeted GPU acceleration where computational returns are highest and implementation risk is lowest.

10.1 Detailed Architectural Specifications

A. Native High-Resolution DSM Raster Ingestion (gridmetrics.exe)

FUSION2 currently processes raw point clouds (.las and .laz). Adding raster input capability enables direct processing of photogrammetric surface models (such as NAIP3D) and gridded point products without converting rasters to intermediate point files.

  • Format Detection and Dispatch: In src/tools/gridmetrics/gridmetrics.cpp, inspect the positional input argument using GDAL driver probing. If the input file extension or header indicates a supported raster format (such as GeoTIFF, VRT, or ENVI) rather than an ASPRS LAS file, route execution to a dedicated raster processing pipeline: 
    // Format dispatch in gridmetrics.cpp
std::filesystem::path inputPath(argv[inputArgIndex]);
bool isRasterInput = false;
GDALDriverH hDriver = GDALIdentifyDriver(inputPath.string().c_str(), nullptr);
if (hDriver != nullptr) {
    // Verified GDAL-compatible raster dataset
    isRasterInput = true;
}
  • Windowed Scanline Block Streaming: Large photogrammetric tiles (such as 10,000 ft × 10,000 ft at 1.0 ft cell size, containing 106 million single-precision float pixels) require 424 MB of RAM for raw elevation storage. To maintain a bounded memory footprint, ingest the DSM raster in horizontal scanline strips (e.g., blocks of 256 or 512 rows) using GDALRaster::ReadBandData: 
    // Windowed scanline streaming buffer
int blockSizeRows = 512;
std::vector<float> dsmBlockBuffer(blockSizeRows * rasterCols);
for (int rowStart = 0; rowStart < rasterRows; rowStart += blockSizeRows) {
    int currentBlockRows = std::min(blockSizeRows, rasterRows - rowStart);
    // Read block window across all columns
    ReadRasterWindow(dsmRaster, 0, rowStart, rasterCols, currentBlockRows, dsmBlockBuffer);
    // Process pixels into active zonal accumulators...
}
  • Spatial Registration and DTM Bilinear Interpolation: For each pixel center \((x, y)\) in the input DSM block, compute its corresponding zonal output grid indices \((col_{zone}, row_{zone})\): \[ col_{zone} = \left\lfloor \frac{x - x_{min}}{\text{cellsize}} \right\rfloor, \quad row_{zone} = \left\lfloor \frac{y_{max} - y}{\text{cellsize}} \right\rfloor \] Evaluate ground elevation \(z_{dtm}\) at \((x, y)\) using bilinear interpolation via groundRaster.GetElevation(x, y, SampleMethod::Bilinear). Compute normalized canopy height: \[ h = z_{dsm} - z_{dtm} \] If \(h \ge \text{minht}\), append \(h\) to the elevation accumulator of the target zone \((col_{zone}, row_{zone})\).
  • Metric Completeness and Compatibility: By populating FUSION2's existing CellAccumulator containers with height values sampled from the raster, all standard metrics computed by ComputePointStatBundle (including mode, average absolute deviation, median absolute deviation, and all four L-moments) are calculated without algorithmic divergence.

B. GPU-Accelerated 2.5D CHM Rasterization (canopymodel.exe)

Generating a Canopy Height Model from unorganized point clouds requires finding the maximum height above ground in each grid cell. This reduction maps directly to device execution without requiring sorting or histogram buffers.

  • Host Memory Buffering & Coordinate Normalization: Allocate pinned host memory (via cudaMallocHost) for streaming point coordinates. To avoid precision degradation from large state plane coordinates (which can exceed \(2 \times 10^6\) ft) in single-precision GPU registers, subtract the tile origin \((x_{min}, y_{max})\) in double precision on the host before uploading: \[ x_{rel} = \text{static\_cast}<\text{float}>(x - x_{min}), \quad y_{rel} = \text{static\_cast}<\text{float}>(y_{max} - y) \]
  • Atomic Integer Reinterpretation Kernel: Because IEEE 754 positive single-precision floating-point numbers have identical binary ordering to signed 32-bit integers, non-negative heights (\(h \ge 0.0\text{ ft}\)) are updated in destination grid memory using hardware-accelerated atomicMax on 32-bit integer representations: 
    // CUDA kernel for atomic CHM rasterization with bounds protection
__global__ void RasterizeCHMKernel(const float* __restrict__ xRel,
                                   const float* __restrict__ yRel,
                                   const float* __restrict__ z,
                                   const float* __restrict__ dtmGrid,
                                   float* __restrict__ chmGrid,
                                   int numPoints,
                                   float cellSize,
                                   int cols,
                                   int rows) {
    int idx = blockIdx.x * blockDim.x + threadIdx.x;
    if (idx >= numPoints) return;

    int c = static_cast<int>(xRel[idx] / cellSize);
    int r = static_cast<int>(yRel[idx] / cellSize);

    // Strict boundary checks
    if (c >= 0 && c < cols && r >= 0 && r < rows) {
        int cellIndex = r * cols + c;
        float ground = dtmGrid[cellIndex];
        float h = z[idx] - ground;
        if (h >= 0.0f) {
            atomicMax(reinterpret_cast<int*>(&chmGrid[cellIndex]), __float_as_int(h));
        }
    }
}
  • Array Initialization and Sentinel Encoding: Initialize the device destination buffer chmGrid to zero (or the IEEE bit-representation of the no-data sentinel value, such as \(-9999.0\text{f}\)) prior to kernel launch. Following execution, copy the raster to host memory and write a standard GeoTIFF via GDALRaster.
  • GPU Spatial Smoothing Pass: When the /smooth:n option is specified, execute a 2D separable Gaussian or box convolution kernel directly on device memory before downloading results to host memory, eliminating intermediate file writes.

C. High-Throughput GPU Raster Zonal Analytics Engine

When porting the 2026_RasterMetrics CUDA kernel into FUSION2, specific modifications are required to resolve the limitations documented in Section 3 and Section 5:

  • Dynamic Per-Zone Histogram Scaling: Rather than enforcing a static global cap (such as 300.0 ft or 450.0 ft), evaluate the maximum height \(Z_{max}\) of each zone during an initial reduction pass across the fine pixels. Allocate 2,048 bins where the bin width is scaled dynamically: \[ \Delta z = \frac{Z_{max}}{2048} \] This eliminates clipping of surface spikes and guarantees consistent bin resolution across short vegetation.
  • Shared-Memory Bitonic Sort Fallback for Sparse Cells: When the count of returns clearing the height break in a zone satisfies \(N < 256\), branch execution to a shared-memory bitonic sort. Evaluate sample percentiles using R's standard type = 7 interpolation formula directly over the sorted elements, achieving exact numerical agreement with reference CPU implementations in sparse forest canopies.
  • Exact Integer Histograms for 8-Bit Spectral Bands: For multi-spectral channels (NAIP Red, Green, Blue, Near-Infrared), allocate exact 256-bin histograms (1,024 bytes per zone). This eliminates quantization error entirely, consumes minimal shared memory, and allows concurrent evaluation of spectral metrics alongside elevation.
