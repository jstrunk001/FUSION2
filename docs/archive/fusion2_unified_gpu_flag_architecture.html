Design Specification

Baking Harmonized GPU Acceleration into FUSION2 via --gpu

Target Project: FUSION2 Architecture CLI Switch: --gpu or /gpu Status: Recommended Architectural Specification Date: October 2026

1. Executive Summary

Yes, baking GPU acceleration directly into FUSION2's existing command-line tools under a single --gpu (or /gpu) switch is entirely feasible and is the cleanest architectural design.

Instead of creating disjoint tools (e.g. rastermetrics.exe vs gridmetrics.exe), the existing tools can seamlessly detect input formats and hardware capabilities. When --gpu is passed:

  • If the input is a Point Cloud (.las, .laz, .copc.laz), it activates the GPU Sparse Raster Binning & Histogram Engine.
  • If the input is a High-Resolution Raster (.tif, .img, .vrt), it activates the Fused Bilinear DTM & Zonal CDF Engine (derived from the Julia pipeline).
  • If no compatible NVIDIA GPU is found, it automatically logs a notice and falls back to the multi-threaded CPU engine without crashing.
Zero Breaking Changes for Existing Users

Existing scripts and automation workflows using FUSION2 syntax continue running identically on CPU by default. Adding /gpu or --gpu simply activates the hardware accelerator, producing bit-for-bit consistent outputs in a fraction of the time.

2. CLI Syntax & Harmonization Across Tools

Because FUSION2's ArgumentParser.h natively treats single-slash (/), single-dash (-), and double-dash (--) transparently and case-insensitively, both --gpu and /gpu work interchangeably:

Example Commands:

# 1. Point Cloud GridMetrics with GPU Acceleration
gridmetrics --gpu /ground:dtm.tif lidar_tile.laz 66.0 metrics.tif

# 2. Raster-to-Raster Canopy Metrics (NAIP3D / Photogrammetry DSM directly in gridmetrics!)
gridmetrics --gpu /ground:dtm.tif dsm_10011.tif 66.0 metrics.tif

# 3. Canopy Height Model (CHM) generation via GPU atomicMax
canopymodel --gpu /ground:dtm.tif points.laz chm.tif

# 4. Individual Tree Top Detection via GPU 2D stencil
canopymaxima --gpu chm.tif /output:tree_tops.csv

# 5. Topographic Terrain Derivatives (Horn's Slope & Aspect via GPU stencil)
topometrics --gpu dem.tif /output:topo.tif

3. Multi-Modal Input Polymorphism in gridmetrics

One of the greatest benefits of this harmonization is that gridmetrics.exe becomes a single, unified canopy metrics engine for both point clouds and rasters:

Input Format Detection CPU Execution Path GPU Execution Path (--gpu)
Point Clouds (.las, .laz) Header / Extension std::vector heap cells + std::sort CUB Radix Sort → Shared-Memory CDF Histogram
Fine Rasters (.tif, .img) GDAL Probe Bilinear resample + CPU zonal aggregation Zero-copy register DTM interpolation + CUDA CDF kernel

4. Internal Engine Architecture

A. Dispatch Logic in gridmetrics.cpp

int main(int argc, char* argv[]) {
    fusion::cli::ArgumentParser parser("gridmetrics", "Gridded canopy metrics from point clouds or rasters");
    // Standard options...
    parser.AddFlag("gpu", "Enable NVIDIA CUDA GPU acceleration (falls back to CPU if unavailable)");

    if (!parser.Parse(argc, argv)) return 0;

    bool wantGpu = parser.HasFlag("gpu");
    bool gpuReady = wantGpu && fusion::cuda::IsCudaAvailable();

    if (wantGpu && !gpuReady) {
        std::cout << "[gridmetrics] Notice: /gpu requested but no compatible NVIDIA GPU detected. Using CPU engine.\n";
    }

    if (IsRasterFormat(inputPath)) {
        if (gpuReady) {
            return RunRasterMetricsCuda(inputPath, groundPath, res, outTif, parser);
        } else {
            return RunRasterMetricsCpu(inputPath, groundPath, res, outTif, parser);
        }
    } else {
        if (gpuReady) {
            return RunPointCloudMetricsCuda(inputPath, groundPath, res, outTif, parser);
        } else {
            return RunPointCloudMetricsCpu(inputPath, groundPath, res, outTif, parser);
        }
    }
}

B. Safe Build & Distribution Architecture

  • Unified Core Library: Add a clean CUDA translation unit (src/libfusion_core/cuda/) containing the CUDA kernels.
  • Static CUDA Runtime (-cudart=static): Statically linking the CUDA runtime ensures the final binaries have zero external DLL dependencies. The user does not need to install the CUDA Toolkit.
  • Multi-Architecture Fatbins: Compiled with CMAKE_CUDA_ARCHITECTURES="75;80;86;89;90;compute_75", ensuring a single binary runs natively across Turing, Ampere, Ada Lovelace, Hopper, and future GPUs via PTX JIT.

5. Benefits for the FUSION2 Suite

1. Clean User Interface

No extra executables or command names to memorize. One flag (--gpu or /gpu) accelerates all supported operations across the entire 15-tool suite.

2. Batch Pipeline Transparency

In pipeline.exe and batch/tiled mode, passing --gpu propagates to all stage child processes (groundfilter → canopymodel → canopymaxima), accelerating the entire workflow.

3. Resilient Portability

Scripts written with --gpu can safely run on any machine—if an NVIDIA GPU is present, it runs at 100× speed; if executed on a CPU-only server, it finishes correctly on the CPU.

6. Conclusion & Next Steps

Baking this harmonization directly into FUSION2 under --gpu combines the raw speed of the Julia GPU raster research with the comprehensive feature set and proven reliability of FUSION2. The transition can be implemented incrementally, starting with gridmetrics and canopymodel.
