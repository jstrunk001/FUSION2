1. Executive Summary

An investigation into the GPU-accelerated raster processing engine in C:\Users\Jacob\Box\sync\R\analyses\2026_RasterMetrics\julia confirms that the mathematical and architectural innovations developed there can provide order-of-magnitude efficiency gains if integrated into FUSION2.

In the Julia pipeline (GpuMetricsPipeline.jl), a fused CUDA kernel paired with a 2,048-bin shared-memory CDF histogram and asynchronous host RAM staging reduced the processing time of a 106-million-pixel tile from 50.0 seconds down to 0.42 seconds (~119× speedup).

Core Performance Finding

By replacing memory-intensive sorting ($O(N \log N)$) with shared-memory atomic histogram accumulation ($O(N)$), percentile and quantile extraction drops into single-digit milliseconds per cell on GPU hardware.

3. Application to Intensity and Spectral Metrics

Yes, the histogram approach is exceptionally well-suited for intensity and spectral (RGB/NIR) metrics—in fact, it provides even greater theoretical and practical advantages for spectral channels than it does for elevation:

Why Spectral Channels Excel Under Histogram Binning

Unlike elevation (which represents continuous, unbounded float heights requiring quantization), 8-bit spectral channels (Red, Green, Blue, NIR) have an inherently discrete domain of exactly 256 integer levels ($0 \dots 255$). A 256-bin histogram provides exact, bit-identical percentiles, median, and mode with zero approximation error.

B. Eliminating FUSION2's Multi-Sort Memory Bottleneck

In the current FUSION2 CPU engine (gridmetrics.cpp), computing elevation, intensity, and spectral metrics incurs catastrophic memory and computational costs:

  • Multiple Vector Allocations: Each grid cell maintains separate dynamically-allocated vectors: cell.elevations, cell.intensities, and cell.extras->spectralValues["red"], ["green"], ["blue"], ["nir"]. Across millions of cells, this results in gigabytes of RAM overhead and severe cache thrashing.
  • Repeated $O(N \log N)$ Sorting: FUSION2 invokes std::sort() separately for elevation, again for intensity, and again for each requested spectral channel—amounting to 4 to 6 separate sorting passes per cell.
  • Single-Pass GPU Streaming Alternative: On the GPU, points stream through thread registers in a single pass. For each point, threads execute atomic increments into concurrent shared-memory histograms (s_hist_elev, s_hist_int, s_hist_rgb) and accumulate register sums for mean/variance. No vectors are allocated, no point coordinates are stored in memory, and no sorting is performed.

C. Shared Memory Footprint

Modern NVIDIA GPUs (Turing, Ampere, Ada Lovelace, Blackwell) provide 64 KB to 128 KB of fast shared memory per Streaming Multiprocessor (SM). Allocating simultaneous histograms for all channels within a single threadblock requires:

D. Natural Calculation of Mode and Strata

  • Mode Calculation: In FUSION2 (PointCloudStats.cpp), the mode (elev_mode, int_mode) is determined by binning sorted values and finding the run with the maximum count. With a histogram, the mode is found natively in a single parallel reduction ($O(B)$) by identifying the bin index with the highest count: argmax(s_hist).
  • Stratification (/strata, /intstrata, /rgbstrata): Because stratum boundaries (e.g., 0–2 m, 2–8 m, 8–16 m) map to fixed bin ranges in the histogram, stratum point counts, proportions, and quantile summaries can be extracted via fast sub-range sums without re-filtering the raw point records.

4. High-Impact Applications for FUSION2

A. New Tool: Native Raster Metrics (rastermetrics)

FUSION2 currently excels at point cloud processing. However, when users process high-resolution DSMs/CHMs (NAIP3D, DAP stereo-imagery, SfM), they must rely on external R or Python scripts. Integrating a native CUDA rastermetrics.exe (or gridmetrics /raster) provides sub-second multi-band GeoTIFF outputs directly from FUSION2.

B. GPU Acceleration for canopymaxima

canopymaxima.exe detects individual tree tops via Variable Window Local Maxima (VLM). Currently implemented as nested CPU loops across rows and columns, it is an ideal candidate for a 2D GPU stencil kernel, dropping search times on 100M-pixel rasters from minutes to milliseconds.

C. Accelerated Stencils in topometrics

Horn's slope and aspect algorithms in topometrics.exe are 3×3 local finite-difference stencils. Offloading these calculations to a simple CUDA kernel provides instantaneous terrain derivative outputs.

D. Point Cloud Metric Reduction in gridmetrics

For ultra-dense point clouds (20M–100M points per tile), the statistical reduction phase in gridmetrics.exe (currently ComputePointStatBundle sorting vectors of points) can be offloaded to a GPU histogram kernel, avoiding per-cell sorting overhead entirely across elevation, intensity, and RGB channels.

5. Technical Implementation Strategy in FUSION2

  • Modular Optional Dependency: FUSION2's minimal, self-contained architecture (~8–15 MB static binaries with zero external DLLs) should be preserved. GPU support should be added via an optional CMake flag: 
    cmake -B build -DENABLE_CUDA=ON
    When compiled without CUDA, the tools build cleanly for standard CPU execution.
  • Output Compatibility: The GPU kernels should output directly to FUSION2's native GDAL raster writer and SQLite table writer (/output-table), ensuring bit-for-bit parity with standard FUSION deliverables.
  • Memory Architecture: Use pinned host memory (cudaHostAlloc) for zero-copy streaming of GDAL raster buffers directly into GPU textures or linear device arrays.

6. Conclusion

Extending the shared-memory histogram approach to intensity and spectral metrics is not only viable—it is mathematically more optimal than elevation because of the bounded discrete nature of color and intensity data. By eliminating multiple sorting passes and multi-gigabyte vector allocations, FUSION2 can achieve uniform, order-of-magnitude speedups across its entire analytical suite.
