Architecture & Strategy

Histogram Optimization & CUDA Integration for FUSION2

Target Project: FUSION2 (C++17 Point Cloud & Raster Engine) Scope: CPU Histogram Staging, CUDA Binary Size, Cross-GPU Portability Date: October 2026

1. Strategy: Should We Implement Histograms on CPU First?

Yes, a two-phase implementation (CPU Histogram Optimization → CUDA GPU Acceleration) is the cleanest, lowest-risk, and most effective engineering path.

Phase 1: CPU-Side Histogram Optimization

What it addresses: In gridmetrics.cpp and PointCloudStats.cpp, the current CPU bottleneck is that every grid cell stores points in raw std::vector<float> buffers and calls std::sort() ($O(N \log N)$) independently for elevation, intensity, and spectral channels.

  • Immediate Spectral Win: For 8-bit RGB and NIR channels ($0 \dots 255$), a stack-allocated 256-element array (uint32_t hist[256] = 1 KB) replaces vector storage and sorting entirely. Quantiles are computed via a sub-millisecond prefix-sum scan, yielding bit-identical metrics with zero sorting.
  • Memory Footprint Discipline: On CPU, allocating full 2,048-bin histograms for all cells across a 5,000 × 5,000 grid simultaneously would consume 10–20 GB of RAM. The CPU implementation can use a streaming cell/row accumulator, populating a histogram only when reducing a completed cell, avoiding high memory overhead.
  • Algorithmic Parity & Golden Tests: Implementing the histogram/CDF quantile extraction functions in C++ first establishes bit-for-bit regression tests against legacy FUSION before any GPU code is introduced.
Phase 2: CUDA Kernel Offloading

What it addresses: Once the histogram logic is verified on CPU, the exact same mathematical functions are ported to CUDA kernels. The GPU handles massive point-in-cell binning in parallel and maintains the histograms inside fast shared memory (scratchpad L1 cache) for in-flight threadblocks.

2. Overhead and Executable Size of the CUDA Approach

A. Binary Size Footprint

FUSION2 executables are currently very compact (~8–15 MB each), compiled statically against minimal GDAL and LASzip with zero external DLL dependencies.

Component Size Impact Notes
Static CUDA Runtime (cudart_static.lib) +4 – 6 MB Eliminates any requirement for cudart64_*.dll on the user machine.
Device Code (SASS Binaries) +2 – 4 MB per GPU Architecture Compiled machine code for target GPU microarchitectures.
Embedded PTX Virtual Assembly +1 – 2 MB Enables JIT compilation for future/unlisted NVIDIA GPUs.
Total Standalone Executable Size ~18 – 25 MB Still exceptionally compact, self-contained, and easily distributable.

B. Runtime & Toolchain Overhead

  • Build-Time Overhead: Requires the NVIDIA CUDA Toolkit (nvcc) installed on the developer/build machine. Builds can take 30–60 seconds longer due to multi-architecture compilation.
  • End-User Requirements: The end user does NOT need the CUDA Toolkit or Visual Studio installed. They only need a standard NVIDIA display driver (version 450+), which provides nvcuda.dll.
  • Runtime Initialization: CUDA context initialization takes ~100–150 ms on the first GPU call. For tiny point clouds (< 500k points), this initialization dominates runtime. For production runs (> 5M points or multi-gigabyte rasters), the 50×–100× speedup dwarfs the 150 ms startup.

3. Generic Executable Across GPUs (Cross-Hardware Portability)

Yes, a single generic CUDA executable can run across virtually all NVIDIA GPUs. In modern CMake and CUDA, this is achieved through Multi-Architecture Fatbins and PTX JIT Forward-Compatibility:

The Universal "Fatbin" Build Pattern

By instructing CMake to compile both native machine code (SASS) for common GPU families and virtual assembly (PTX) for baseline architectures, the resulting binary runs natively on older cards and automatically JIT-compiles on brand-new architectures at first launch.

CMake Architecture Specification:

# Multi-Architecture Fatbin targeting Turing, Ampere, Ada Lovelace, and Blackwell
# with PTX forward-compatibility fallback:
set(CMAKE_CUDA_ARCHITECTURES "75;80;86;89;90;compute_75")
Architecture Compute Capability Target GPU Examples Deployment Status
Turing sm_75 GTX 1660, RTX 2060–2080, Quadro RTX 4000/5000/6000 Pre-compiled native SASS
Ampere sm_80, sm_86 RTX 3050–3090, RTX A4000–A6000, A100 Pre-compiled native SASS
Ada Lovelace sm_89 RTX 4060–4090, RTX 4000–6000 Ada Pre-compiled native SASS
Hopper / Blackwell sm_90, sm_100 H100, B200, next-gen consumer RTX 50-series Native / PTX JIT
Future / Unlisted GPUs compute_75 (PTX) Any future NVIDIA architecture Driver automatically JITs embedded PTX at runtime

Graceful CPU Fallback (Non-NVIDIA or Headless Systems)

If a user runs the executable on a system without an NVIDIA GPU (e.g. an AMD/Intel machine or a bare cloud node): 

int deviceCount = 0;
cudaError_t err = cudaGetDeviceCount(&deviceCount);
if (err != cudaSuccess || deviceCount == 0) {
    std::cout << "[FUSION2] No compatible NVIDIA GPU detected. Falling back to multi-threaded CPU engine...\n";
    RunCpuPipeline();
} else {
    RunCudaPipeline();
}

4. Summary Recommendations

  1. Implement Phase 1 (CPU Histogram Optimization): Refactor ComputePointStatBundle and gridmetrics' spectral and intensity processing to use fixed-bin histograms, eliminating vector sorting and verifying identical statistical output.
  2. Preserve the Default CPU Binary: Keep FUSION2's lightweight (~10 MB) pure-CPU distribution as the standard build so users without CUDA toolchains can build and run seamlessly.
  3. Add an Optional CMake Target for CUDA: Use -DENABLE_CUDA=ON with static CUDA runtime linking to create a universal, self-contained ~20 MB binary with multi-architecture SASS and PTX fallback.
